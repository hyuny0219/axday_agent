# BOARDROOM 2026 — v0.9 UX 수정안 (검토용): 이해도·반복 제거·회의록 타임라인

작성일 2026-09-13 · 대상 기준: main 커밋 138e275 (P0 + 디자인 마감 머지 상태) · 형식은 v0.6/v0.7 수정안과 같다: `대상 → 현재 → 문제 → 수정안 → 적용 후 확인`

## 0. 계기와 검토 방법

Render 배포본을 실제로 체험한 뒤 나온 피드백 두 가지다.

1. 안건을 고르고 자료 E1~E4를 읽고 의견을 내는 흐름이 **잘 이해되지 않는다.**
2. 의견(DISCUSS)과 추가 의견(REACTIONS 후속)을 두 번 내는 것이 **반복처럼 느껴진다.** 아예 실제 회의처럼 흘러가는 **채팅 형식**은 어떤가.

이 문서는 원인을 진단하고 세 가지 안(A 최소 수정 / B 회의록 타임라인 / C 완전 채팅형)을 비교한 뒤 권장안을 낸다. **표결 규칙·조건 ID·세션 reducer는 바꾸지 않는다.** 바뀌는 것은 화면의 프레이밍·순서·입력 방식이다. 검토는 두 갈래로 한다: (a) Codex가 PR #3에서 구현 관점(240초 예산·접근성·scripted/live 동등성·규칙 엔진 영향)을 검토하고, (b) GPT가 기획 관점에서 각 항목을 채택/수정 채택/기각으로 판정해 `docs/REVISION_DECISIONS_v0.9.md`에 남긴다.

## 1. 진단 — 왜 브리핑에서 의견까지가 어려운가

- **대상:** BRIEFING·OPINIONS·DISCUSS 화면, `docs/SCENARIO_AI_ASSISTANT.md` 브리핑 절.
- **현재:** 원안 한 문장 → 자료 카드 4장(각 한 줄) → AI 정리 카드 → [의견 듣기] → 임원 4명의 한 줄 의견 → [내 의견 말하기] → 추천 문구 6개 + 300자 입력.
- **문제:**
  1. **결정 질문이 없다.** "무엇을 정하는 회의인가"가 화면에 없다. 원안은 "AI 업무 비서를 도입한다…미정이다"로 끝나 참가자는 찬반 대상을 스스로 추론해야 한다. 의장 대사(`chairLine`)는 이미 BRIEFING 상단에 렌더되지만("보고 준비에 쓰던 시간을 판단과 실행에 돌려줄 수 있을까요?…") 수사적 질문이라 결정 대상·조건·내 역할을 알려 주지 않는다.
  2. **자료가 결론 없이 나열된다.** E1 "120건, 검토 완료", E2 "126건, 검토 전"은 숫자 불일치를 스스로 발견해야 의미가 생긴다. 각 카드에 "이 자료가 말하는 것"(찬성 근거인지 우려 근거인지, 어느 임원이 이걸 근거로 삼는지)이 없다.
  3. **조건(PILOT·REVIEW·ACCESS·MEASURE)이 너무 늦게 나온다.** 이 체험의 실제 레버는 "어떤 조건을 붙여 안건을 고칠 것인가"인데, 조건은 DISCUSS의 추천 문구를 고른 뒤에야 칩으로 드러난다. 참가자는 브리핑 시점에 "내가 할 수 있는 일"을 모른다.
  4. **역할 안내가 없다.** 명패 "나 · 특별 이사"는 있지만 "특별 이사가 이 4분 동안 하는 일 = 조건을 붙여 의견을 내고 한 표를 던진다"가 어디에도 없다. 진행 단계도 헤더 pill 하나뿐이라 전체 여정이 보이지 않는다.
  5. **4분 타이머가 브리핑부터 돈다.** 읽는 동안 시간이 줄어 서둘러 넘긴다.
- **수정안(A-1, 모든 안에 공통):**
  1. BRIEFING 상단의 기존 `chairLine` 자리를 **의장 브리핑 블록**으로 확장한다: 상황 한 문장("주간 보고마다 부서 자료를 손으로 모읍니다. 이걸 AI 비서에 맡길지 정합니다"), 결정 질문("도입할까요? 한다면 어떤 조건을 붙일까요?"), 특별 이사의 역할 한 줄("이사님은 조건을 붙여 의견을 내고, 마지막에 한 표를 던집니다"). 데이터는 `chairLine`(string)을 `chairBriefing {situation, question, role}`로 바꾸고 기존 문장은 `situation`의 첫 문장으로 흡수한다.
  2. 자료 카드 4장에 **"이 자료가 말하는 것"** 한 줄과 **관련 임원 아바타**를 붙인다. 예: E1·E2 "같은 일의 건수가 자료마다 다르다 → CAIO: 출처·기준일 확인 필요", E3 "취합이 반복된다 → CEO·CFO: 자동화 효과 기대", E4 "권한 설계가 안 끝났다 → CISO: 권한 확인 먼저". 시나리오 문서의 기존 표를 데이터로 옮기므로 새 사실을 만들지 않는다.
  3. AI 정리 카드를 **"핵심 쟁점 3개"** 형식으로 바꾼다: ① 숫자가 자료마다 다르다(E1·E2) ② 검토 담당자가 없다(E3) ③ 권한·공유 범위가 미정이다(E4). 문장은 현재 `briefingSummary`를 그대로 쪼갠 것이다.
  4. BRIEFING 하단에 **조건 미리보기** "이사님이 붙일 수 있는 조건"으로 PILOT·REVIEW·ACCESS·MEASURE 라벨 4개를 읽기 전용 칩으로 보여 준다. 클릭은 DISCUSS에서 한다.
  5. 헤더 아래에 **진행 스트립** "① 상황 파악 → ② 임원 의견 → ③ 내 의견 → ④ 반응에 답하기 → ⑤ 표결"을 상시 표시하고 현재 단계를 강조한다.
  6. **타이머는 BRIEFING을 읽는 동안 멈추지 않는다**(240초 규칙 유지)가, BRIEFING의 [의견 듣기] 옆에 "남은 시간은 충분합니다"를 표시해 재촉감을 줄인다. 초 단위 권장은 넣지 않는다(판정 1-6). 시간 규칙은 바꾸지 않는다.
- **적용 후 확인:** 처음 보는 사람 3명이 설명 없이 BRIEFING을 읽고 "무엇을 정하는지"와 "내가 뭘 할 수 있는지"를 한 문장으로 말할 수 있어야 한다(현장 검수 항목으로 FACILITATOR_GUIDE에 추가).

## 2. 진단 — 왜 의견 두 번이 반복처럼 느껴지는가

- **대상:** DISCUSS·REACTIONS 화면, 시나리오 "첫 반응 및 후속 질문" 절.
- **현재:** DISCUSS에서 문구 선택 + 300자 입력 + 조건 칩 확인 → [의견 전달]. REACTIONS에서 내 발언 인용 + 임원 반응 4장 + 후속 질문("메일과 실적표의 숫자가 다르면…") + 선택지 3개 + 300자 입력 + 조건 칩 → [보완 의견 전달] 또는 [앞선 의견 유지].
- **문제:**
  1. 두 화면의 **입력 폼이 같은 모양**(선택지 + 큰 textarea + 칩)이라 "같은 걸 또 시킨다"로 읽힌다.
  2. 후속 질문의 **목적이 화면에 없다.** 이 질문은 "숫자 불일치를 어떻게 다룰지"로 REVIEW 조건을 유도하는 장치인데, 누가 왜 묻는지 표시가 없다.
  3. 임원 반응이 한 줄씩 카드로 나열되어 **대화가 아니라 게시판**처럼 보인다. 내 발언에 대한 응답이라는 인과가 약하다.
- **수정안(A-2):**
  1. REACTIONS의 후속 입력을 **의장의 질문 + 빠른 답 3개**로 줄인다. textarea는 기본 접힘("직접 답하기"를 눌러야 열림). 조건 칩은 답을 고른 뒤에만 나타난다. 기본 강조 버튼은 "앞선 의견 유지"가 아니라 첫 번째 선택지로 두되, 어느 것도 미리 선택하지 않는다.
  2. 후속 질문에 **발화자와 이유**를 붙인다: "CAIO가 묻습니다 — 자료마다 숫자가 다른데, 그대로 공유해도 될까요?" 시나리오의 공통 질문을 CAIO 발화로 귀속(근거 E1·E2와 일치).
  3. 임원 반응 카드를 **내 발언 아래에 답글 형태(들여쓰기·연결선)**로 배치하고, 변한 임원만 강조하고 나머지는 "기존 의견 유지"로 흐리게 한다(현재 라벨 유지).
  4. 화면 제목을 "임원들의 반응"에서 **"이사님 의견에 대한 반응 — 한 가지만 더 여쭙겠습니다"**로 바꿔 두 번째 입력이 '보완'이 아니라 '질문에 답하기'임을 드러낸다.
- **적용 후 확인:** (1) 후속 단계에서 텍스트 입력 없이 버튼만으로 완주 가능(E2E "추천 문구만으로 완주" 유지). (2) **직접 입력만으로 완주** 경로도 그대로 보존한다(지시서 7장 P0 기준): 접힌 편집기를 마우스·키보드(Tab → Enter)로 열고 포커스가 textarea로 이동해 입력·제출까지 되는지 `e2e/flow-full.spec.ts`의 직접 입력 경로를 갱신해 검증한다. (3) 후속 단계 평균 체류가 40초 이하.

## 4. B안 상세 — 회의록 타임라인

- **구성:** 상단 고정: 헤더·명패·진행 스트립·안건 한 줄. 본문: 타임라인(의장 브리핑 → 자료 4장(접힘 가능) → 핵심 쟁점 3개 → 임원 4명 첫 의견 → **[내 차례]** 추천 문구 quick reply + 작성기 → 내 발언 → 임원 반응(답글) → CAIO의 후속 질문 + 빠른 답 3개 → 내 답 → **임원 후속 발언(FOLLOWUP, live에서는 "판단 중…" 후 도착)** → 의장 "이 조건으로 안건을 고정합니다" → MOTION 화면으로 전환).
- **FOLLOWUP 대기(live):** 현재 구현은 후속 제출 즉시 reducer가 MOTION으로 넘어가고 그 뒤에 `runRound('FOLLOWUP')`이 돌며, 최종표 요청은 그 라운드 뒤에 직렬화된다. 타임라인이 MOTION 전에 끝나면 이 최대 8초가 숨은 대기가 되고, 참가자가 바로 안건을 고정·투표하면 `awaitResult()`의 8초 예산까지 잠식해 임원 표가 UNCAST로 확정될 수 있다. 따라서 B에서는 (a) 후속 제출 뒤 타임라인에 임원 후속 블록을 "판단 중…"으로 노출하고, **`runRound('FOLLOWUP')`이 돌려준 promise가 settle된 뒤에만** 의장 블록과 [안건 고정으로] CTA를 활성화하거나(별도의 벽시계 8초 타이머로 열지 않는다: 앞 라운드가 아직 사슬에 남아 있으면 FOLLOWUP의 8초 상한은 그 뒤에야 시작하므로, 제출 시각 기준 8초는 FOLLOWUP이 대기열에 있는 채로 안건 고정·투표를 허용해 UNCAST 문제를 재현한다. 라운드 자체가 8초에서 절단되므로 promise 대기가 곧 상한 대기다), (b) reducer의 `SUBMIT_FOLLOWUP → MOTION` 전이를 유지하되 MOTION 화면 상단에 같은 "후속 판단 중…" 블록을 두고 최종표 시작을 지금처럼 사슬 뒤에 둔다. 권장은 (a)이며, 이 경우 화면 전이 시점만 늦추고 reducer는 바꾸지 않는다(MOTION 전이는 그대로, 타임라인이 MOTION 단계의 첫 블록을 함께 그린다). 표결 대기 예산(8초)은 FOLLOWUP 완료 뒤에 시작하도록 `awaitResult()` 호출 시점을 확인한다.
- **입력:** 내 차례 블록만 입력 가능. 나머지는 읽기 전용. quick reply는 현재 PhraseCard와 같은 복수 선택(체크)이며, 선택 시 작성기에 문장이 조합된다(현재 DraftEditor 재사용). 조건 칩은 작성기 아래 그대로.
- **live:** 임원 블록은 "판단 중…" 점 세 개 → 발언 도착 시 교체. 응답 실패는 "응답 없음"으로 남긴다(현재 상태 칩 재사용).
- **라운드별 실패 상태 보존:** `Session.roleStatus`는 역할당 값 하나이고 새 라운드가 시작되면 전원 `pending`으로 덮이며, 실패는 transcript에 남지 않는다. 누적 타임라인에서 "OPINIONS에서 CAIO 응답 없음"을 유지하려면 도메인 변경 없이 **화면 쪽 라운드 기록**을 둔다: App 상태에 `roundLog: { stage, roleId, status }[]`를 두고 orchestrator의 라운드 결과(answered/failed)를 stage와 함께 기록한다(reducer 밖, 공개 payload에도 넣지 않음). 리셋 시 비운다. **stage 전달 경로:** 현재 `SET_ROLE_STATUS` 액션에는 roleId·status만 있어 App에서 가로채도 어느 라운드인지 알 수 없고, 전원 실패 시에는 stage가 있는 `APPEND_STATEMENTS`도 발생하지 않는다. 따라서 `SET_ROLE_STATUS`에 선택 필드 `stage?: StatementStage`를 추가하고 `runRoundNow(stage)`가 이를 채워 dispatch한다. reducer는 이 필드를 읽지 않으므로(타입만 확장, 동작 불변) 도메인 규칙에는 영향이 없고, App의 dispatch 래퍼가 `stage`가 있는 SET_ROLE_STATUS만 roundLog에 적는다. 대안(orchestrator deps에 `onRoundStatus(stage, roleId, status)` 콜백 추가)도 가능하나 dispatch 한 경로로 두는 편이 테스트가 단순하다. 대안으로 실패를 `Statement`로 저장하는 방식은 transcript가 모델 프롬프트에 들어가므로 채택하지 않는다.
- **접근성:** 새 블록이 추가될 때 `aria-live="polite"`로 발화자와 첫 문장을 읽어 준다. 내 차례 블록으로 포커스 이동. 키보드만으로 완주하는 E2E 유지.
- **1280×720:** 자료 4장과 쟁점은 접힘 상태로 시작(제목만), 내 차례 블록이 항상 화면 안에 오도록 자동 스크롤.
- **자동 스크롤과 무입력 시계:** `App.tsx`는 전역 `scroll` 이벤트를 참가자 활동(TOUCH)으로 집계한다. 새 블록 도착 시 프로그램이 스크롤하면 90초 무입력 시계가 연장되어 방치 세션이 초기화되지 않는다. 자동 스크롤은 `scrollIntoView` 전후에 억제 플래그를 세워 그 사이의 scroll 이벤트를 무시하거나, `wheel`·`keydown`·`pointerdown`·`touchstart`로 시작된 스크롤만 활동으로 세도록 바꾼다. 단위 테스트: 자동 스크롤 뒤 `lastActivityAt`이 변하지 않는다.
- **관람 화면(P1):** 타임라인의 공개 블록만 복제하면 되므로 관람 뷰와도 잘 맞는다.
- **바뀌지 않는 것:** 단계 상태기계, reducer, 조건·표결 규칙, 240초·무입력 규칙, MOTION·VOTE·RESULT.
