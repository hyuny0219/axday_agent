# 프롬프트 v14 튜닝 기록 (T122, 2026-10-11)

## 문제

v13 live 실측(`tuning-v13.md`)에서 조건을 모두 넣고도 임원이 찬성으로 넘어오는 비율이 3/12(v11은 10/12)였다. 원인은 두 가지였다.

- live 임원이 첫 반응(REACTIONS)에서 각자 다른 새 질문("누가 언제 확인하나", "실제 손해 금액은")을 던졌다. 화면은 시나리오의 추가 질문(`followUp.question`) 하나만 보여 주므로 참가자가 그 질문에 답해도 임원은 "내 질문에는 답이 없다"며 반대를 유지했다.
- 평가 세트의 FOLLOWUP·VOTE 요청에는 참가자의 추가 질문 답변 문장이 없어, 질문에 답한 경로를 제대로 재지 못했다.

사용자 선택: "임원 질문을 화면의 추가 질문 하나로 맞추고 다시 측정".

## 바꾼 것

**프롬프트 (`server/prompts/common.ts`, `server/handlers/round.ts`·`vote.ts`)**

- REACTIONS: meeting_record에 화면의 추가 질문 하나와 질문자를 싣고, 역할별로 규칙을 붙인다(`buildReactionsQuestionRule`). 새 질문을 따로 만들지 말고 남은 우려는 평서문으로만 말한다. 질문자는 그 질문의 뜻으로만 묻고, 질문자가 아닌 임원은 "질문자의 질문에 대한 답을 기다리겠습니다"에 해당하는 뜻만 말한다.
- FOLLOWUP·VOTE: 회의 기록에 참가자의 답변 문장을 싣고(`참가자의 답변 문장`) `ANSWER_JUDGMENT_RULE`을 붙인다. 답이 질문에 답했고 확정 조건이 우려를 덜어 줬다면 참가자 쪽으로 확정해도 되고, 답이 질문을 비껴갔다면 그 점을 근거로 판단한다.
- `PROMPT_VERSION` v13 → v14. v13의 FOLLOWUP 방향 단어 금지 규칙과 서버 교정은 그대로다. 표결 규칙표(domain)·T110 게이트·화면 문구는 바꾸지 않았다.

**클라이언트→서버 전달 (`src/services/boardAgents/live.ts`)**

- 확인 결과 FOLLOWUP 요청의 `participantOpinion`은 마지막 의견(= 답변)이라 이미 답변 문장이 실렸지만, 어느 질문에 대한 답인지는 없었고 VOTE 요청에는 답변도 질문도 없었다.
- round·vote 요청에 선택 필드 `followUpQuestion`(`askedBy`, `question`)과 `followUpAnswerText`(≤300자)를 추가했다. 질문은 화면과 같은 기준(T93 입장별 질문)으로 고른다. REACTIONS는 지금 의견의 입장, 답변 뒤(FOLLOWUP·VOTE)는 질문을 보여 준 입장(`followUpStance`)이다. 답변 문장은 답했을 때(두 번째 의견이 있을 때)만 싣는다. 필드를 생략한 기존 요청의 동작은 그대로다. scripted 모드는 영향이 없다.

**평가 (`scripts/eval-set-run.ts`, `scripts/eval-set.json`)**

- 답한 케이스마다 `followUpAnswerText`(그 안건·입장의 `followUp.options` 중 확정 조건과 맞는 문장, 조건이 없으면 질문에 직접 답하지 않는 중립 문장)를 두고, 실행기가 REACTIONS·FOLLOWUP·VOTE 요청에 질문과 답변을 싣는다. FOLLOWUP의 `participantOpinion`은 실제 앱처럼 답변 문장이다.
- 새 지표 `첫 반응 새 질문(질문자 외)`: REACTIONS 행 중 질문자가 아닌 임원의 발언에 `?`·까요·나요·습니까·입니까·궁금이 들어 있는 비율(표지가 없는 간접 질문은 못 잡는 보수적 규칙). v13 기록도 같은 규칙으로 다시 쟀다.

**mock**: 질문자만 "추가 질문 하나를 묻습니다", 나머지는 "질문자의 질문에 대한 답을 기다립니다"(의문문 없음)로 말한다.

## live 실측 결과 (claude-sonnet-5, 평가 세트 22케이스, 344행)

실행 두 번. 1차(`tuning-v14-after-run1.jsonl`)에서 experience-first 조건 보완 케이스의 답변을 "결정 결과를 돌아보고…"(REVIEW 문장)로 골랐는데, 이 안건의 추가 질문은 "데이터가 위험하다고 알려도 경험을 따르겠는가, 멈추겠는가"라서 그 답은 질문에 직접 답하지 않았다. 임원이 "멈출지 답이 명확하지 않습니다"를 근거로 반대했다(규칙대로의 판단). 평가 세트의 답변 선택 오류이므로 질문에 직접 답하는 DATA_VETO 문장으로 고쳐 2차(`tuning-v14-after.jsonl`)를 돌렸다. 프롬프트는 두 실행 사이에 바꾸지 않았다.

## 판단

- **목표 달성.** 조건 보완 → YES 12/12(목표 ≥ 9/12), 새 질문 31/65 → 1/64, 방향 누설 화면 0 유지, 금지 어휘·존댓말 악화 없음(오히려 감소).
- **의도한 부작용 확인.** 답이 질문을 비껴가면 임원이 그 점을 근거로 반대한다(1차 experience-first). 이것이 `ANSWER_JUDGMENT_RULE`의 두 번째 갈래이고, 실제 앱에서는 참가자가 질문에 맞지 않는 추천 답변을 고르면 같은 일이 생긴다. 추천 답변은 질문에 직접 답하는 문장으로 쓰여 있어 정상 흐름에서는 문제가 없다.
- **주의할 변화 두 가지.** (1) 상충 경로(EXP_ONLY+DATA_VETO)에서 찬성이 0/16 → 2/15가 됐다. 실제 앱은 충돌 조건을 동시에 확정하지 못하므로 평가 세트 고유 경로이고, 답변이 질문에 직접 답한 것을 임원이 근거로 든 결과다. (2) FOLLOWUP 원시 방향 표현이 1/80 → 3/80으로 늘었다. 모두 서버 교정으로 중립 문장이 되어 화면 노출은 0이다. 두 건은 한 실행의 표본이라 변동 범위 안일 수 있다.
- **실패 행.** provider_error·invalid_response 9행은 두 실행에서 위치가 달라 프롬프트 때문이라는 증거가 없다(형식 오류 시도는 schema 3건, 120자 초과 등).
