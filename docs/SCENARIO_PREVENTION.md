# 안건 ③ — 검증한 AI 서비스를 어디까지 확대할까?

> **v0.8 적용:** [임원 에이전트 명세](AGENT_BOARDROOM_SPEC.md)를 먼저 적용한다. 이 파일의 자료·추천 문구·조건 확인·원안 정규화는 live/scripted 공통이다. 고정 반응·표결 우선순위·대표 경로의 득표수는 scripted 테스트 데이터이며 live 에이전트의 정답이나 강제 표가 아니다. live는 동일 최종안과 실제 논의로 각 임원이 판단한다.

버전 2.1 · 2026-09-09 · v0.7 P1 구현 기준. 모든 사업장 수·기간·의견·규칙은 체험용 가상 데이터다. 사고 감소나 실제 회사의 성과를 뜻하지 않는다.

## 원안과 기본 조건

원안 `prevention-scale`: 12개 사업장에서 6개월 시범 운영한 점검 보조 AI 서비스를 다음 분기 50개 사업장으로 확대한다. 기존 검토·중단 절차와 정보 이용 동의·접근 절차는 확대에도 유지한다.

기본 조건 `BASE_REVIEW`, `BASE_CONSENT`는 원안에 이미 포함된다. 참가자가 재언급하거나 체크하지 않아도 유효하다. 원안에는 50개 운영을 위한 인력·부하 계획이 아직 없다. 확대 승인은 준비 완료와 다르며 실행 전 남은 과제를 항상 표시한다.

## 브리핑 자료

| ID | 카드 | 가상 내용 |
| --- | --- | --- |
| E1 | 파일럿 기록 | 12개 사업장·6개월. 검토 담당자 1명이 운영했고 점검 이행 기록이 있다. 사고 감소 효과는 판단하지 않았다. |
| E2 | 고객 의견 | 10개 사업장은 연장 의향, 2개는 불필요한 알림을 지적했다. 신규 50개 수요를 입증한 것은 아니다. |
| E3 | 확대 운영 | 검토·중단 절차는 운영 중이다. 50개 확대 시 갱신 부하·담당자 증원은 검토 전이다. |
| E4 | 정보·투자 | 확대에도 동일한 동의·접근 절차를 적용하는 원안이다. 대상별 실제 동의 확인과 확대 비용·지표 기준 확정은 남아 있다. |

AI 자동 정리 카드(자료 옆 상시 표시, ‘체험용 사전 구성’): “시범 운영 기록과 연장 의향은 있습니다(E1·E2). 사고 감소 효과는 미판단입니다(E1). 기존 검토·동의 절차는 유지하지만 확대 인력·갱신 부하(E3), 신규 대상 동의와 투자 기준(E4)을 확인해야 합니다.”

| CISO | 원안의 동의·접근 절차 유지를 지지합니다. 대상별 확인 후 연결해야 합니다. | E4 |

## 추천 문구와 구조화 변경

| ID | 문구 | 변경 ID |
| --- | --- | --- |
| P1 | 담당자 증원과 데이터 갱신 부하 계획을 확대 착수 조건으로 넣읍시다. | CAPACITY_PLAN |
| P2 | 50개를 한 번에 연결하지 말고 단계별 점검 후 확대합시다. | STAGED_SCALE |
| P3 | 유용성·이탈·운영 부담과 비용을 확인하고 다음 투자를 판단합시다. | VALUE_TRACK |
| P4 | 확대는 재심의하고, 확대 인력·부하 검증만 먼저 승인합시다. | TARGETED_CHECK |
| P5 | 같은 범위의 파일럿을 6개월 더 반복하고 확대를 다시 심의합시다. | REPEAT_PILOT |
| P6 | 대상별 동의 절차를 생략하고 정보를 연결합시다. | DROP_CONSENT |

STAGED_SCALE/TARGETED_CHECK/REPEAT_PILOT은 상호 배타적이다. 충돌 시 참가자가 최종 진행 방식을 고르고 이전 초안은 보존한다. 나머지는 조합 가능하다. TARGETED_CHECK는 구체적인 미검증 항목 검토이며 합리적인 대안이다. REPEAT_PILOT도 자동 실패나 함정으로 분류하지 않는다. 새 검증 목적이 있으면 직접 입력과 TARGETED_CHECK 확인으로 표현할 수 있다.

## 최종 안건 구성

- 기본 executionMode=SCALE. STAGED_SCALE이면 STAGED_SCALE, TARGETED_CHECK이면 VALIDATE_FIRST, REPEAT_PILOT이면 REPEAT_FIRST로 바꾼다. VALIDATE_FIRST/REPEAT_FIRST는 확대를 현재 승인하지 않고 검증·재심의를 승인하는 안건이다.
- effectiveConditions는 원안 BASE_REVIEW/BASE_CONSENT에 확인한 추가 조건을 합친다. DROP_CONSENT는 BASE_CONSENT를 명시적으로 제거하는 변경이다. 원안 포함 조건을 선택 여부로 제거하지 않는다.
- 변경이 없는 발언은 원안 재확인으로 기록하고 kind=original을 유지한다. 의미가 달라지는 추가·삭제·진행 방식 변경이 있으면 kind=amended다.
- 표결 규칙은 동일한 최종 안건의 executionMode와 effectiveConditions를 평가한다. 표결 전 최종안에 유지/추가/삭제/보류할 실행을 구분하고 참가자가 확인한 뒤 고정한다.

## 반응과 후속 질문

| 변경 | 반응 |
| --- | --- |
| CAPACITY_PLAN | CAIO: “인력·갱신 부하 계획을 착수 조건으로 반영하겠습니다. 실제 검증은 남습니다.” |
| STAGED_SCALE | CFO: “단계별 투자 범위와 확인할 지표를 함께 정합시다.” |
| VALUE_TRACK | CFO: “유용성·운영 부담·비용을 다음 투자 판단 근거로 삼겠습니다.” |
| TARGETED_CHECK | CAIO: “미검증인 확대 인력·부하에 집중하는 검증에 찬성합니다.” |
| REPEAT_PILOT | CFO: “같은 시험을 반복하는 비용과 지연을 설명해 주세요. 새로 확인할 질문이 필요합니다.” |
| DROP_CONSENT | CISO: “원안의 정보 동의 절차를 삭제한 안건에는 반대합니다.” |
| 변경 없음 | CEO: “기존 절차를 유지한 원안으로 심의합니다. 확대 운영 과제는 남아 있습니다.” |

후속 질문: “50개 사업장을 현재 담당자 1명으로 운영할 수 있을지 아직 모릅니다. 어떻게 하시겠습니까?”

- “증원·부하 계획을 착수 조건으로 넣읍시다.” → CAPACITY_PLAN 제안.
- “확대 부하를 먼저 시험한 뒤 다시 심의합시다.” → TARGETED_CHECK 제안; 기존 진행 방식과 충돌 확인.
- “앞선 의견 유지” → 변경 없음.
- 직접 입력 → 원문 보존, 허용 변경을 제안하고 참가자가 확인. 자유 입력만으로 표·조건을 자동 확정하지 않는다.

## 임원 표결 우선순위

아래 표현의 조건은 최종 안건에서 평가한다. ‘동의 없음’은 BASE_CONSENT가 유효하지 않은 경우다. 각 임원에서 처음 참인 행 하나만 적용한다.

| 임원 | 조건 | 표 |
| --- | --- | --- |
| CEO | 동의 없음 | HOLD |
| CEO | VALIDATE_FIRST 또는 REPEAT_FIRST | HOLD |
| CEO | 나머지 | YES |
| CFO | 동의 없음 | NO |
| CFO | REPEAT_FIRST | NO |
| CFO | VALIDATE_FIRST | HOLD |
| CFO | STAGED_SCALE 및 VALUE_TRACK | YES |
| CFO | 나머지 | HOLD |
| CAIO | 동의 없음 | NO |
| CAIO | VALIDATE_FIRST | YES |
| CAIO | REPEAT_FIRST | HOLD |
| CAIO | CAPACITY_PLAN | YES |
| CAIO | 나머지 | NO |
| CISO | 동의 없음 | NO |
| CISO | 나머지 | YES |

CISO는 원안의 정보 조건으로 찬성 가능하다. CAIO의 반대는 ‘기존 검토 절차 미선택’ 때문이 아니라 확대 용량 계획 부재 때문이다. 제안한 착수 조건에 찬성하는 것과 실제 검증 완료를 구분한다. 과반 기준은 YES≥3 가결 / NO≥3 부결 / 나머지 보류, 전체5석이다.

## 대표 경로

임원 순서: CEO / CFO / CAIO / CISO. 검증안 가결과 확대 가결의 의미를 구분한다.

| 확인 변경 | 임원 표 | 참가자 | 집계·결론 |
| --- | --- | --- | --- |
| 없음 (원안) | YES / HOLD / NO / YES | YES | 찬성3·보류1·반대1, 가결 |
| 없음 (원안) | YES / HOLD / NO / YES | HOLD | 찬성2·보류2·반대1, 보류 |
| 없음 (원안) | YES / HOLD / NO / YES | NO | 찬성2·보류1·반대2, 보류 |
| CAPACITY_PLAN, STAGED_SCALE, VALUE_TRACK | YES / YES / YES / YES | YES | 찬성5, 가결 |
| CAPACITY_PLAN, STAGED_SCALE, VALUE_TRACK | YES / YES / YES / YES | NO | 찬성4·반대1, 가결 |
| STAGED_SCALE, VALUE_TRACK | YES / YES / NO / YES | YES | 찬성4·반대1, 가결 |
| TARGETED_CHECK | HOLD / HOLD / YES / YES | YES | 찬성3·보류2, 가결 |
| TARGETED_CHECK | HOLD / HOLD / YES / YES | NO | 찬성2·보류2·반대1, 보류 |
| REPEAT_PILOT | HOLD / NO / HOLD / YES | YES | 찬성2·보류2·반대1, 보류 |
| DROP_CONSENT | HOLD / NO / NO / NO | YES | 찬성1·보류1·반대3, 부결 |
| 없음 (원안) | YES / HOLD / NO / YES | UNCAST | 찬성2·보류1·반대1·미표결1, 보류 |


③에는 참가자 반대 한 표가 반대3표를 만들어 부결을 성립시키는 경로는 없다. 다만 원안에서 참가자 YES는 가결, NO/HOLD는 보류로 결론에 영향을 준다. 원안 승인과 반대 결정 경로가 원리상 양립 불가능한 것은 아니며 현재 규칙의 특성이다. ①②의 양방향 결정 표와 구분한다.

P1만 추가하면 임원 YES/HOLD/YES/YES로 확대안이 가결될 수 있다. 이는 ‘조건 개수 맞히기’ 난이도가 아니라 확대/단계 확대/선검증 중 실행 방식을 판단하는 설계다. P1과 P4는 함께 선택 가능하며 그 경우 검증안을 심의한다. 두 문구는 승인 대상이 다르며 결과가 반드시 반대라는 뜻은 아니다.

추천 카드 꼬리표: P1 ‘운영 준비 조건’, P2 ‘단계 확대 제안’, P3 ‘성과 추적 조건’, P4 ‘선검증·확대 재심의’, P5 ‘반복검증·확대 재심의’, P6 ‘정보 절차 변경’. 꼬리표는 토론 제안 유형이며 승인·투표 상태가 아니다. 최종 실행 방식은 모든 확인 변경을 정규화한 뒤 MOTION에서 하나만 표시한다. SCALE=‘확대안’, STAGED_SCALE=‘단계 확대안’, VALIDATE_FIRST=‘검증안(확대 재심의)’, REPEAT_FIRST=‘반복 검증안(확대 재심의)’. RESULT도 같은 안건 종류와 그 안건의 가결/보류/부결을 함께 표시한다.

## 결과와 운영

- SCALE/STAGED_SCALE 가결: “확대안이 승인되었습니다. 착수 전 남은 조건을 확인합니다.”
- VALIDATE_FIRST 가결: “확대 인력·부하 검증안이 승인되었습니다. 확대는 재심의합니다.”
- REPEAT_FIRST 가결인 경우에도 확대 승인으로 쓰지 않는다. 현재 규칙에서 이 진행 방식은 가결에 도달하지 않으며 자동 실패 점수를 부여하지 않는다.
- 보류는 현재 최종 안건의 재검토, 부결은 현재 최종 안건의 부결이다. TARGETED_CHECK 안건 부결을 ‘확대 부결’로 잘못 표현하지 않는다.
- 남은 과제: 신규 대상 동의 확인, 인력·갱신 부하 검증, 확대 비용·유용성 기준 확정. 조건이 추가돼도 완료로 표시하지 않는다.
- 정상 완주 결과에는 자동 자료 정리 데모 표시를 포함하고 추가 도움은 실제 사용 기록만 표시한다. 실제 모델 호출과 사전 구성을 구분한다.
- 고정 안건 없이240초 만료하면 기본 절차가 포함된 원안으로 집계하고 참가자는 UNCAST다. 무입력90초 복귀는 집계 없이 초기화한다.
- 입력300자·최종 확인·마우스·운영·관람 뷰는 [구현 지시서](../CLAUDE_IMPLEMENTATION.md)를 따른다.
