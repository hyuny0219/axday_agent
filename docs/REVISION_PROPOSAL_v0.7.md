# BOARDROOM 2026 — 기획안 v0.7 수정안 (검토용)

작성일 2026-09-09 · 대상 기준: main 커밋 6d7916d (기획서 v0.6, 구현 지시서 1.3, 시나리오 ① 1.1 / ② 1.1 / ③ 2.0, 디자인 명세, VALIDATION_v0.6, FACILITATOR_GUIDE)

## 0. 이 문서의 목적과 검토 방법

v0.6 반영분을 검토한 결과다. v0.6의 표결 규칙은 독립 열거로 재검증했고(①② 96경로, ③ 128경로, 대표 경로 전부 일치, 네 임원 모두 찬성 경로 존재) 문제가 없다. 아래는 그 위에서 새로 발견한 다섯 가지이며, 모두 P0 착수를 막지 않는다. 형식은 v0.6 수정안과 같다: `대상 → 현재 → 문제 → 수정안 → 적용 후 확인`.

검토자(GPT)에게 요청하는 것:

1. 각 항목을 채택 / 수정 채택 / 기각으로 판정하고 이유를 한 줄로 남긴다. 결과는 `docs/REVISION_DECISIONS_v0.7.md`에 기록한다.
2. 채택 항목은 대상 파일에 반영하고 기획서 변경 이력에 v0.7 절을 추가한다. 구현 지시서는 1.4로 올린다.
3. 표결 규칙은 이번 수정안에서 바꾸지 않는다. 규칙 재검증은 필요 없다.

우선순위: **P-필수**(P1 착수 전), **P-문서**(문서 한두 줄).

## 1. 관람 뷰 동기화의 브라우저 프로필 제약 — P-필수

- **대상:** `CLAUDE_IMPLEMENTATION.md` 3장 "P1 관람 뷰", 7장 완료 기준, `docs/FACILITATOR_GUIDE.md` 검수 문단, 기획서 12장 장비.
- **현재:** 관람 뷰는 "같은 PC·같은 origin에서 BroadcastChannel로 공개 데이터만 동기화"하고, 참가자 앱이 2초 heartbeat를 보내며 5초 끊김이면 대기 화면으로 전환한다. 창을 어떻게 띄우는지는 정하지 않았다.
- **문제:** BroadcastChannel과 localStorage 이벤트는 **같은 브라우저 프로필** 안에서만 전달된다. 두 모니터에 키오스크 창을 하나씩 띄우려고 Chrome을 `--user-data-dir`를 달리해 두 번 실행하면 두 창은 서로 다른 프로필이 되어 동기화가 전혀 되지 않는다. 현장에서 가장 흔한 실행 방식이 바로 이것이라, P1 막바지나 리허설에서 발견되면 동기화 방식을 통째로 바꿔야 한다.
- **수정안:**
  1. 지시서 "P1 관람 뷰" 절에 실행 규칙을 추가한다.
     > 관람 창은 참가자 앱의 운영 메뉴에서 '관람 창 열기'로 `window.open('?view=spectator')`를 호출해 연다. 열린 창을 두 번째 모니터로 옮긴 뒤 그 창에서 전체화면을 요청한다. 두 창은 반드시 같은 브라우저 인스턴스·같은 프로필이어야 한다. `--user-data-dir`를 달리한 두 인스턴스, 시크릿 창, 다른 브라우저 조합은 지원하지 않는다. 브라우저 정책으로 팝업이 막히면 운영 메뉴에 관람 뷰 URL을 표시해 같은 창에서 새 탭으로 열고 탭을 드래그해 분리하는 대안을 안내한다.
  2. 운영 메뉴 항목에 '관람 창 열기'를 추가한다(기존: 새 체험·전체화면 진입·전체화면 종료·닫기).
  3. 대안 경로를 미리 적어 둔다.
     > 같은 프로필 두 창이 현장 장비에서 불가능하면 로컬 WebSocket 릴레이(같은 PC의 localhost, 공개 payload만 중계)로 교체한다. 관람 뷰의 payload·revision·heartbeat 규칙은 전송 계층과 무관하게 유지한다. 전송 계층을 어댑터로 분리해 두 방식이 같은 인터페이스를 쓰게 한다.
  4. 완료 기준과 진행 가이드 검수 항목에 추가한다.
     > 두 창이 각각 다른 모니터에서 전체화면인 상태로 동기화·초기화·재접속이 동작한다. 브라우저 재시작 후 운영 메뉴만으로 두 창을 복구할 수 있다.
  5. 기획서 12장 장비에 "참가자 PC 한 대에 모니터 두 대(참가자용·관람용) 연결, 확장 모드"를 명시한다. 관람 화면을 별도 PC로 두는 구성은 WebSocket 릴레이가 있을 때만 가능하다.
- **적용 후 확인:** 지시서에 창 실행 방식, 지원하지 않는 조합, 대안 경로, 검수 항목이 모두 있다. 리허설 2(실제 장비) 완료 조건에 두 창 동기화가 들어간다.

## 2. 안건 ③의 결정 경로 성격 명시 — P-문서

- **대상:** `docs/SCENARIO_PREVENTION.md` 대표 경로 절, `docs/VALIDATION_v0.6.md`(또는 v0.7), 기획서 13장 검증 항목.
- **현재:** 검증 문서는 세 시나리오 공통으로 "참가자 표의 결정/불변 경로"를 확인했다고 쓴다. 기획서 13장은 "참가자 표가 결론을 바꾸는 경로와 바꾸지 않는 경로 모두 정상 동작"을 요구한다.
- **문제:** ③에서는 참가자 표가 결론을 바꾸는 경로가 **찬성 방향에만** 있다. 임원 반대가 2표가 되는 조합이 없어서 참가자의 반대가 부결을 만드는 경로는 없다(DROP_CONSENT는 참가자 표와 무관하게 부결). 이것은 원안 승인 경로와 맞바꾼 설계 결과이지 오류가 아니지만, 문서가 세 안건을 같은 문장으로 묶고 있어 구현자가 ③에도 반대 결정 경로 테스트를 기대할 수 있다.
- **수정안:**
  - 시나리오 ③ 대표 경로 절 끝에 추가: "③에는 참가자의 반대가 결론을 바꾸는 경로가 없다. 참가자 표는 찬성 방향(원안 가결, 검증안 가결)에서만 결정적이다. 이는 원안 승인 경로를 두기 위한 설계이며 ①②의 양방향 결정 경로와 다르다."
  - 검증 문서 표에 열을 추가한다.

    | 시나리오 | 찬성 결정 경로 | 반대 결정 경로 | 원안 승인 |
    | --- | --- | --- | --- |
    | ① | 있음 | 있음 | 없음 |
    | ② | 있음 | 있음 | 없음 |
    | ③ | 있음 | 없음(설계) | 있음 |

  - 기획서 13장 해당 항목을 "①②는 찬성·반대 양방향, ③은 찬성 방향의 결정 경로를 확인한다"로 고친다.
- **적용 후 확인:** 엔진 테스트 명세가 시나리오별로 다른 기대치를 갖는다.

## 3. 안건 ③ P1·P4의 구분과 난이도 — P-문서

- **대상:** `docs/SCENARIO_PREVENTION.md` 추천 문구 표·최종 안건 구성, 디자인 명세 MOTION 화면, 기획서 8장.
- **현재:** P1 "담당자 증원과 데이터 갱신 부하 계획을 확대 착수 조건으로 넣읍시다"(CAPACITY_PLAN)와 P4 "확대 인력·부하만 먼저 검증하고 확대안을 다시 심의합시다"(TARGETED_CHECK)는 둘 다 확대 인력·부하를 다룬다. 결과는 정반대다. P1은 조건부 **확대 승인**, P4는 확대를 미루고 **검증만 승인**한다. 또 P1 하나만 확인해도 임원 표가 YES/HOLD/YES/YES가 되어 참가자 표와 무관하게 확대가 가결된다.
- **문제:** 4분 안에 두 문구의 차이를 읽기 어렵다. 그리고 가장 눈에 띄는 문구 하나로 확대가 통과되므로 ③이 세 안건 중 가장 쉬운 안건이 됐다. 의도한 것일 수 있으나 명시돼 있지 않다.
- **수정안:**
  - P4 문구를 "확대는 재심의하고, 확대 인력·부하 검증만 먼저 승인합시다"로 바꿔 진행 방식이 문장 앞에 오게 한다. P1은 그대로 둔다.
  - 추천 문구 카드에 실행 방식 꼬리표를 붙인다: P1·P2·P3은 "확대 승인", P4 "검증 후 재심의", P5 "반복 후 재심의", P6은 꼬리표 없음. 디자인 명세 컴포넌트 절에 "③에서만 문구 카드 우측에 실행 방식 꼬리표"를 추가한다.
  - MOTION 화면 상단에 실행 방식을 안건명과 같은 크기로 표시한다: "확대안" / "단계 확대안" / "검증안(확대 재심의)" / "반복 검증안".
  - 난이도는 규칙을 바꾸지 않고 기획서 8장에 한 문장으로 명시한다: "③은 근거가 갖춰진 안건이라 조건 하나로도 확대가 가결될 수 있다. 판단의 무게는 통과 여부가 아니라 확대·단계·검증 중 어느 실행 방식을 고르느냐에 있다."
- **적용 후 확인:** P1·P4 문구가 서로 다른 동사로 시작한다. MOTION 화면과 결과 화면에 실행 방식이 표시된다.

## 4. 안건 선택 목업과 선택 문구 정리 — P-문서

- **대상:** `docs/design/DESIGN_SPEC.md` 1장 표·8장, 기획서 5장 안건 선택표.
- **현재:** 명세 8장은 result.png와 PPT만 "v0.5 시각 참고, 표결 수치 적용 제외"로 표시한다. agenda-select.png의 ③ 카드는 "AI 예방 서비스 / 사고가 나기 전에 도울 수 있을까?"인데 ③의 새 제목은 "검증한 AI 서비스를 어디까지 확대할까?"다. 기획서 5장 ③ 선택 문구는 "검증한 서비스를 어디까지 확대할까요?"로 의문문이고, ①②는 "고객이 너무 오래 기다립니다", "보고 준비만 하다 하루가 갑니다"로 1인칭 서술이다.
- **수정안:**
  - 명세 1장 표의 안건 선택 행 용도를 "3개 카드·선택 강조(v0.5 시각 참고, ③ 문구 적용 제외)"로 바꾸고, 8장 첫 문단에 agenda-select.png를 추가한다.
  - 기획서 5장 ③ 선택 문구를 서술형으로 맞춘다: "파일럿은 끝났습니다. 이제 얼마나 확대할까요."는 여전히 의문이 섞이므로 "시범 운영이 끝났고, 확대 규모를 정해야 합니다."를 제안한다. 카드 부제는 시나리오 ③ 제목을 그대로 쓴다.
- **적용 후 확인:** 구버전 이미지 세 종(PPT, result.png, agenda-select.png)이 같은 표기로 묶인다. 세 선택 문구가 같은 어조다.

## 5. P0 범위 고정 — P-문서

- **대상:** `CLAUDE_IMPLEMENTATION.md` 2장 구현 순서, 6장 데이터·엔진 설계.
- **현재:** v0.6에서 Motion에 baseConditionIds·effectiveConditionIds·executionMode가 추가됐고, 관람 뷰 payload·revision·heartbeat 규칙, 서기 입력, 실제 AI 실패 처리가 들어와 지시서가 1.0 대비 두 배 가까이 커졌다. P0(안건 ②)에 무엇이 필요하고 무엇이 P1인지가 6장에는 구분돼 있지 않다.
- **문제:** 첫 구현이 ③ 전용 구조와 P1 관람 프로토콜까지 한꺼번에 떠안으면 P0 완주가 늦어진다. 반대로 P0에서 Motion 형태를 단순하게 만들면 P1에서 데이터 모델을 갈아엎게 된다.
- **수정안:** 6장 Motion 정의 아래에 P0 규칙을 추가한다.
  > P0는 Motion 인터페이스를 v1.3 그대로 정의하되 값은 고정한다: `baseConditionIds = []`, `effectiveConditionIds = conditionIds`, `executionMode = 'DEFAULT'`. 표결 규칙 평가기는 effectiveConditionIds와 executionMode를 입력으로 받도록 처음부터 만든다. ③의 기본 조건 병합·실행 방식 정규화는 P1에서 시나리오 데이터에 정규화 함수를 추가하는 방식으로 구현하며 인터페이스는 바꾸지 않는다.

  2장 구현 순서의 P0 항목에 "관람 뷰·서기 모드 UI·실제 AI 어댑터는 P0 범위 밖. 단, 공개 payload를 만드는 selector 함수는 P0에서 정의해 P1 관람 뷰가 그대로 쓰게 한다"를 덧붙인다.
- **적용 후 확인:** P0 완료 기준에 ③ 전용 항목과 관람 뷰 항목이 없다. P1 착수 시 Motion 인터페이스 변경이 필요 없다.
