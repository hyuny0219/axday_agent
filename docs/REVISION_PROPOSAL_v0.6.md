# BOARDROOM 2026 — 기획안 v0.6 수정안 (검토용)

작성일 2026-09-09 · 대상 기준: main 커밋 dc43015 (기획서 v0.5, 구현 지시서 1.2, 시나리오 ①②③ 1.0, 디자인 명세)

## 0. 이 문서의 목적과 검토 방법

이 문서는 현재 기획안을 행사 관점에서 검토한 결과를 **적용 가능한 수정안** 형태로 정리한 것이다. 각 항목은 `대상 → 현재 → 문제 → 수정안 → 적용 후 확인` 순서로 쓴다. 수정안은 제안이며, 채택 여부는 검토자가 정한다.

검토자(GPT)에게 요청하는 것:

1. 각 수정안을 채택 / 수정 채택 / 기각으로 판정하고 이유를 한 줄로 남긴다.
2. 채택한 항목은 대상 파일에 직접 반영하고, 기획서 변경 이력에 v0.6 절을 추가한다.
3. 표결 규칙을 바꾸는 항목(A-1, B-1)은 반영 후 **허용 조건 조합 × 참가자 YES/HOLD/NO/UNCAST 전수 열거**로 아래 불변식을 검증한다.
   - 모든 임원 규칙은 어떤 조건 조합에도 정확히 한 행이 일치한다(총괄성).
   - 전체 의석은 항상 5석이고 각 의석은 1표다.
   - 가결·보류·부결이 모두 도달 가능하다.
   - 참가자 표가 결론을 바꾸는 경로와 바꾸지 않는 경로가 모두 존재한다.
   - 함정 조건(OPEN_ALL 계열)이 있으면 참가자 표와 무관하게 부결이다.
4. 문서 간 정합성을 확인한다. 같은 규칙·수치·용어가 기획서, 구현 지시서, 시나리오 3종, 디자인 명세, README에서 서로 다르지 않아야 한다.

우선순위 표기: **P-필수**(행사 전 반드시), **P-방향**(콘텐츠 방향 결정, 빠를수록 좋음), **P-운영**(운영 준비).

## A. 관객과 행사 맥락

### A-1. CISO에게도 찬성 경로를 준다 — P-필수

- **대상:** `docs/SCENARIO_AI_ASSISTANT.md`, `docs/SCENARIO_CUSTOMER_SUPPORT.md`, `docs/SCENARIO_PREVENTION.md`의 "가상 임원 표결 규칙"과 "조건별 반응", `AX_Day_2026_Boardroom_Plan.md` 3장.
- **현재:** 세 안건 모두 CISO 규칙이 `함정 있음 또는 권한 조건 없음 → NO / 권한 조건 있음 → HOLD`이며 YES 행이 없다. CEO·CFO·CAIO는 모두 YES 경로가 있다.
- **문제:** 기획서 3장은 "특정 직책이 모든 위험을 전담하는 것으로 표현하지 않는다"고 명시하지만 규칙은 CISO를 세 안건 모두에서 유일하게 찬성하지 못하는 인물로 만든다. 실제 삼성화재 CISO가 체험하면 "정보보호는 늘 발목을 잡는 역할"로 읽힌다.
- **수정안 (1안, 최소 변경):** CISO 규칙에 "네 개 허용 조건이 모두 확인됨 → YES" 행을 최우선 조건 다음에 추가한다.

  | 임원 | 우선순위 조건 | 최종 표 |
  | --- | --- | --- |
  | CISO | 함정 조건 있음 | NO |
  | CISO | 네 허용 조건 모두 있음 (예: ② PILOT·REVIEW·ACCESS·MEASURE) | YES |
  | CISO | 권한 조건 있음 (② ACCESS / ① DATA_ACCESS / ③ DATA_SCOPE) | HOLD |
  | CISO | 나머지 | NO |

  반응 문구 추가: "권한·검토·파일럿·측정 조건이 모두 갖춰져, 착수 전 실제 권한 검증을 전제로 찬성합니다."
  대표 경로 첫 두 행은 `YES / YES / YES / YES`로 바뀌며 결론은 그대로 가결이다. 그 외 경로는 변하지 않는다.
- **수정안 (2안, 역할 순환):** 안건마다 "검증이 남아 보류를 유지하는 임원"을 바꾼다. ① CAIO(연계·이관 절차 실검증), ② CISO(권한 실검증), ③ CFO(확대 후 첫 지표 확인). 변경 폭이 크므로 1안을 우선 검토하고, B-1(안건 ③ 재설계)을 채택할 경우에만 ③에 한해 2안을 적용한다.
- **적용 후 확인:** 세 안건 모두에서 CEO·CFO·CAIO·CISO 각각 YES 행이 최소 하나 존재한다. 기획서 3장 원칙과 규칙표가 모순되지 않는다. 결과 화면의 CISO 카드에 YES 상태 색·문구가 준비된다.

### A-2. 진행 요원 가이드와 서기 모드 — P-운영

- **대상:** 신규 파일 `docs/FACILITATOR_GUIDE.md`, 기획서 12장, 구현 지시서 4장.
- **현재:** 진행 멘트 한 줄("오늘은 특별 이사로 참여하십니다…")만 있다.
- **문제:** C레벨 부스 체험의 만족도는 화면보다 옆에 선 사람이 결정한다. 임원은 키보드를 직접 치기보다 말로 의견을 내는 경우가 많다.
- **수정안:** 아래 구성의 가이드 초안을 신규 파일로 만든다.

  | 구간 | 시간 | 진행 요원 행동 | 금지 |
  | --- | --- | --- | --- |
  | 맞이 | 0:00 이전 | "오늘 특별 이사로 모십니다" + 명패 안내 + 안건 3개 한 줄 소개, 선택 유도 | 특정 안건 추천 |
  | 브리핑 | 0:00–0:50 | 자료 4장과 AI 정리 카드를 가리키며 "AI가 자료 차이를 먼저 짚어 두었습니다" | 절감률·효과 수치 언급 |
  | 임원 의견 | 0:50–1:30 | "네 분 의견이 갈립니다. 어느 쪽에 가까우신가요?" | 정답 암시 |
  | 발언 | 1:30–2:15 | 추천 문구 안내. 임원이 말로 의견을 내면 **서기 모드** | 문구 대신 골라 주기 |
  | 반응·후속 | 2:15–2:50 | 임원 반응 읽어 주기, 후속 질문 한 번 | 재촉 |
  | 최종 안건·투표 | 2:50–3:20 | "이 안건으로 표결합니다. 한 표를 행사해 주세요" | 표 권유 |
  | 결과 | 3:20–4:00 | 결론·내 조건 반영·남은 과제 30초 해설, 출력물(B-4 채택 시) 전달 | 승패 표현 |
  | 퇴장 | — | "이사님의 의견은 회의 기록에 남았습니다" + 운영 메뉴로 새 체험 | 이전 참가자 화면 노출 |

  **서기 모드 규칙:** 진행 요원이 참가자의 말을 그대로 textarea에 입력하고 소리 내어 읽어 확인받은 뒤, **참가자가 직접 '의견 전달'을 클릭**한다. 조건 칩 확인도 참가자가 클릭한다. 이렇게 하면 구현 지시서 4장의 "참가자가 확인한 구조화 입력" 원칙이 유지된다. 진행 요원은 문구를 요약·수정하지 않는다.
- **적용 후 확인:** 구현 지시서 4장에 "서기 입력은 허용하되 전달·확인 클릭은 참가자" 문장이 추가된다. 리허설 체크리스트에 진행 요원 시연 항목이 들어간다.

### A-3. 관람 화면을 P0/P1로 당긴다 — P-운영

- **대상:** 구현 지시서 2장(구현 순서)·3장·7장, 기획서 11장 "선택적 확장", 디자인 명세.
- **현재:** "별도 관람 화면"은 이후 확장(P2 이후)이다. 부스 콘셉트 이미지의 핵심 비주얼은 대형 화면이다.
- **문제:** 단말 1대 기준 시간당 12명이라 기조연설 직후 대기열이 생긴다. 대기자가 표결 장면을 보는 것이 유입 장치인데 구현 계획에 없다.
- **수정안:**
  - **P0:** OS 화면 복제로 참가자 화면을 대형 모니터에 그대로 출력한다. 완료 기준에 "1920×1080 복제 출력, 3m 거리에서 임원 카드·표결 결과·결론 판독 가능"을 추가한다. 단, 참가자의 직접 입력(textarea)이 그대로 노출되므로 진행 요원 가이드에 "직접 입력 중에는 관람 화면 노출을 알린다"를 넣는다.
  - **P1:** 같은 앱에서 `?view=spectator` 창을 열어 별도 관람 뷰를 만든다. 상태 동기화는 BroadcastChannel 또는 localStorage 이벤트로 같은 PC 안에서 처리해 네트워크 없이 동작하게 한다. 관람 뷰는 ATTRACT·OPINIONS·REACTIONS(임원 반응만)·VOTE 결과·RESULT만 표시하고 DISCUSS의 입력 내용은 표시하지 않는다.
- **적용 후 확인:** 구현 순서표에 관람 뷰가 P1로 명시된다. 관람 뷰에서 참가자 원문이 노출되지 않는다는 완료 기준이 있다.

### A-4. 손에 들고 나가는 결과물을 결정한다 — P-운영

- **대상:** 기획서 10·11·14장, 구현 지시서 3장 RESULT 행·7장, 디자인 명세.
- **현재:** 회의 결과 카드는 화면 열람뿐이고 QR·출력은 확장 항목이다.
- **문제:** 임원에게는 인쇄물 한 장이 화면보다 오래 남고 행사 후 대화의 소재가 된다. 장비 조달 기간과 결과 화면 레이아웃에 영향을 주므로 지금 결정해야 한다.
- **수정안:** 다음 세 가지 중 하나를 14장 "착수 시 확정할 항목"에 결정 항목으로 추가하고 기본안을 (a)+(b)로 둔다.
  - (a) **의결서 출력:** 80mm 감열 영수증 프린터. 오프라인, 출력 5초 내. RESULT 화면에 '의결서 출력' 버튼(1회, 재출력은 운영 메뉴). 내용: 안건명, 결론, 5인 표, 내가 확인한 조건, 남은 과제, "체험용 가상 설정" 문구, 날짜. 실명·개인정보 없음. 브라우저 인쇄는 키오스크 인쇄 플래그(Chrome `--kiosk-printing`)로 대화상자 없이 처리한다.
  - (b) **특별 이사 명패:** 사전 인쇄한 카드형 명패를 착석 시 제공하고 가져가게 한다. 개발 영향 없음.
  - (c) **없음:** 화면 열람만.
- **적용 후 확인:** (a) 채택 시 상태표 RESULT 행에 출력 동작, 완료 기준에 인쇄 레이아웃 캡처, 장비 목록에 프린터가 추가된다.

## B. 콘텐츠와 메시지

### B-1. 안건 ③을 "근거가 충분한 확대 판단" 안건으로 재설계한다 — P-방향

- **대상:** `docs/SCENARIO_PREVENTION.md` 전체, 기획서 5장 안건 선택표·8장.
- **현재:** 세 안건 모두 정답 행동이 "작게 시작·검토 부착·권한 확인·측정 후 확대"로 같다. 함정은 모두 "검증 없이 즉시 확대/자동화"다. 원안 승인은 세 안건 모두 도달 불가다.
- **문제:** AI 전환을 독려하는 AX Day에서 게임이 일관되게 보상하는 행동이 "조건을 붙여 늦추기"다. 거버넌스 메시지로는 옳지만 세 안건의 성격이 같고, 과감한 판단이 근거 있는 선택이 되는 경험이 없다.
- **수정안:** 안건 ③만 "파일럿이 끝나 근거가 있는 상태에서 확대를 판단"하는 안건으로 바꾼다. 함정을 양쪽에 둔다.

  **원안** `prevention-scale`: 12개 사업장에서 6개월 시범 운영한 AI 예방 서비스를 다음 분기 50개 사업장으로 확대한다. 시범 운영의 검토·중단 절차와 정보 동의 절차는 유지한다.

  **자료 카드 (가상)**

  | ID | 카드 | 내용 |
  | --- | --- | --- |
  | E1 | 시범 운영 기록 | 12개 사업장, 6개월. 알림 검토 담당자 1명이 운영. 점검 이행 기록 보유. 사고 감소 효과는 기간이 짧아 판단하지 않음. |
  | E2 | 참여 사업장 의견 | 10개 사업장이 연장 의향. 2개 사업장은 불필요 알림을 지적. |
  | E3 | 운영 여건 | 검토·중단 절차 운영 중. 50개 확대 시 데이터 갱신 부하와 담당자 증원은 검토 전. |
  | E4 | 데이터·투자 메모 | 시범 사업장 정보 동의 절차 확정. 확대 사업장에도 같은 절차 적용 필요. 단계별 투자 기준은 첫 분기 지표로 확정 예정. |

  **추천 문구와 조건**

  | 문구 | 문장 | 조건 |
  | --- | --- | --- |
  | P1 | 다음 분기 50개 사업장으로 단계 확대합시다. | STAGED_SCALE |
  | P2 | 시범 운영의 검토·중단 절차를 확대에도 유지합시다. | KEEP_REVIEW |
  | P3 | 확대 사업장에도 같은 정보 동의 절차를 적용합시다. | CONSENT_FLOW |
  | P4 | 확대 후 유용성·이탈·운영 부담 지표를 추적합시다. | VALUE_TRACK |
  | P5 | 확대 전에 6개월 파일럿을 한 번 더 반복합시다. | REPEAT_PILOT (과잉 신중 함정) |
  | P6 | 동의 절차 없이 전 사업장 정보를 즉시 연결합시다. | DROP_CONSENT (과속 함정) |

  충돌: STAGED_SCALE ↔ REPEAT_PILOT, CONSENT_FLOW ↔ DROP_CONSENT. ③에는 "검증 자료 요청" 문구를 두지 않고 직접 입력으로 대체한다.

  | CAIO | DROP_CONSENT 있음 | NO |
  | CAIO | 네 허용 조건 모두 있음 | YES |
  | CAIO | KEEP_REVIEW 있음 | HOLD |
  | CAIO | 나머지 | NO |
  | CISO | DROP_CONSENT 있음 | NO |
  | CISO | 나머지 | YES (동의 절차가 원안에 이미 포함) |

  | 네 조건 모두 | YES / YES / YES / YES | 임의 | 가결 |
  | STAGED_SCALE, VALUE_TRACK | YES / YES / NO / YES | 임의 | 가결 |
  | KEEP_REVIEW만 | YES / HOLD / HOLD / YES | YES | 가결; HOLD·NO면 보류 |
  | REPEAT_PILOT (+KEEP_REVIEW) | HOLD / NO / HOLD / YES | 임의 | 보류 — 과잉 신중은 재심의 |
  | REPEAT_PILOT, KEEP_REVIEW 없음 | HOLD / NO / NO / YES | NO | 찬성1·보류1·반대3, 부결 — 반대 결정 경로 |
  | DROP_CONSENT | HOLD / NO / NO / NO | 임의 | 부결 |

  기획서 5장 안건 선택표의 "난이도" 열을 "성격" 열로 바꾼다: ① 범위와 품질 설계, ② 신뢰와 권한, ③ 확대 판단.
- **주의:** CONSENT_FLOW는 표를 바꾸지 않고 최종 안건 문구와 남은 과제에만 반영된다. 이것이 허용되는지 검토자가 판단한다. 허용하지 않으면 CISO 규칙을 "DROP_CONSENT → NO / CONSENT_FLOW 또는 네 조건 모두 → YES / 나머지 → HOLD"로 바꾸되, 이 경우 원안 승인 경로가 사라진다.
- **적용 후 확인:** 0절의 불변식 전수 검증. 기획서 13장 "원안 승인을 만들려고 규칙을 임의로 바꾸지 않는다" 문장은 "③은 설계상 원안 승인이 가능하다"로 보완한다. BRIEFING 자동 정리 카드 문구를 새 자료 카드에 맞춰 다시 쓴다(사고 감소 효과 미판단을 반드시 포함).

### B-2. 실제 AI 연동의 우선 기능과 네트워크 결정 — P-방향

- **대상:** 기획서 11·14장, 구현 지시서 2장(P2)·5장.
- **현재:** 상시 표시 카드로 AI 노출은 해결됐지만 카드에 "체험용 사전 구성"이 붙는다. P2 실제 연동은 선택이며 네트워크 조건은 미정이다.
- **문제:** 임원은 "사전 구성"을 녹화된 데모로 인식한다. 실제 모델이 개입하는 순간이 하나도 없으면 효율 메시지는 개념 설명에 그친다.
- **수정안:**
  - 14장에 "행사장 네트워크" 결정 항목을 추가하고, 결정에 따라 P2 범위를 고정한다.

    | 네트워크 | P2 범위 |
    | --- | --- |
    | 있음(유선 또는 테더링 확보) | **"내 발언 정리" 한 기능만 실제 모델** 연결. 입력은 참가자 원문·허용 조건 ID·근거 ID, 출력은 300자 이내 초안과 사용한 근거 ID뿐. 새 사실·수치·표를 생성하지 않도록 스키마 검증. 5초 timeout 시 사전 문구로 전환. 나머지 AI 기능은 사전 구성 유지. |
    | 없음 | 전부 사전 구성. ATTRACT와 RESULT에 "사전 구성 시뮬레이션" 표기를 본문 크기로 노출하고, "AI 비서실장" 명칭은 유지하되 "(시연)" 표기를 붙인다. |
  - 우선 기능을 "내 발언 정리"로 정하는 이유를 11장에 한 문단으로 남긴다: 참가자가 방금 쓴 문장을 다듬는 기능은 개인적이고 사실을 생성하지 않아 위험이 낮으며 효과가 눈에 보인다.
- **적용 후 확인:** P2 완료 기준에 "모델 응답 실패 시 5초 내 사전 문구 전환, 결과 기록에 mode=live/scripted 구분"이 있다.

## D. 지난 검토에서 남은 소항목

### D-1. 참가자 한 표가 가결과 부결을 오가는 경로를 대표 경로에 추가 — P-필수

- **대상:** 시나리오 ①②(③은 B-1 채택 시 별도) 대표 경로표, 결과 문구.
- **현재:** CAIO "검토 조건 없음 → NO" 규칙으로, 파일럿·측정 조건만 확인하고 검토·권한 조건이 없으면 임원 표가 `YES / YES / NO / NO`가 된다. 참가자가 YES면 가결, NO면 부결, HOLD면 보류다. 대표 경로에 없다.
- **수정안:** 대표 경로에 아래 행을 추가하고 결과 문구에 양방향 "이사님의 한 표가 결론을 결정했습니다"를 준비한다. 결론이 같은 경우에는 이 문구를 쓰지 않는다(기획서 10장 원칙 유지).

  | 조건 | 임원 표 | 참가자 | 결론 |
  | --- | --- | --- | --- |
  | PILOT, MEASURE (② 기준) | YES / YES / NO / NO | YES | 찬성3·반대2, 가결 |
  | 동일 | 동일 | NO | 찬성2·반대3, 부결 |
  | 동일 | 동일 | HOLD | 보류 |

- **적용 후 확인:** 세 결론이 같은 조건에서 참가자 표만으로 갈리는 테스트가 있다.

### D-2. 모바일 요건을 P0 완료 기준에서 제외 — P-필수

- **대상:** 구현 지시서 5장("모바일 바텀시트"), 7장("768px/390px 세로 레이아웃"), 디자인 명세 3장("640px 미만", "safe-area·visual viewport").
- **현재:** PC 마우스·물리 키보드로 확정했지만 모바일 요건이 남아 있다.
- **수정안:** 해당 문장을 삭제하거나 "선택(터치 단말 도입 시)"으로 표시한다. 추가 도움 패널은 "사이드 패널"로만 정의한다. 1920×1080과 1280×720 두 해상도만 완료 기준으로 남긴다.
- **적용 후 확인:** 완료 기준에 768px·390px·640px가 없다.

### D-3. 버전과 이력 표기 정리 — P-운영

- **대상:** 기획서 머리말·17장, README.
- **현재:** 기획서는 v0.5인데 마지막 이력 절은 "v0.4 검토 반영"이고, 마우스 확정 커밋의 이력이 없다. 같은 절에 "한글 터치 키보드 기준을 명시"와 "터치 키보드 요건은 대체" 두 문장이 공존한다. 작성일이 09-07로 고정돼 있다.
- **수정안:** 17장을 "v0.4–v0.5 검토 반영"으로 고치고 마우스 확정을 v0.5 항목으로 추가한다. "터치 키보드 기준을 명시" 문장은 "물리 키보드 한글 입력 기준을 명시"로 바꾼다. 머리말에 "최종 수정일" 항목을 추가한다. 이 문서의 채택 항목은 v0.6 절로 기록한다.
