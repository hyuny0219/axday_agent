# 에이전트 작업 방식 — 빌드·검토·수정 반복

버전 1.0 · 2026-09-09 · 대상: docs/DEV_PLAN.md의 P0~P2, 작업 카드는 docs/TASKS.md

## 1. 구성

| 역할 | 정의 파일 | 하는 일 | 하지 않는 일 |
| --- | --- | --- | --- |
| 오케스트레이터 | 이 세션(Claude Code 본체) | 작업 순서 결정, 워크플로 실행, 결과 요약 보고, 막힌 작업 분할, 푸시, PR | 코드 작성 |
| builder | `.claude/agents/builder.md` | 작업 카드 하나 구현, 검사 실행, 커밋, 120단어 이내 보고 | 카드 밖 범위, 푸시, 문서 전체 읽기 |
| reviewer | `.claude/agents/reviewer.md` | 해당 작업 커밋의 diff 검토, 검사 실행, 판정과 발견 사항 최대 10개 | 파일 수정, diff 재서술 |
| task-cycle | `.claude/workflows/task-cycle.js` | 작업 하나에 대해 build → review → (fix → review) 반복, 최대 `maxRounds`회 | 작업 여러 개 연속 실행 |

기본 모델은 builder·reviewer 모두 sonnet이다. 엔진 작업(T04·T06·T07)의 검토는 `reviewModel: "opus"`로 올릴 수 있다.

## 2. 한 작업의 흐름

```
[오케스트레이터] task-cycle 실행 (args: {task:"T04", maxRounds:2})
   └─ Build   builder: 카드 읽기 → 구현 → 검사 → 커밋 → 보고
   └─ Review  reviewer: 커밋 diff 검토 → 검사 실행 → PASS / FIX / BLOCKED
   └─ Fix     (FIX이고 must/should가 있으면) builder: 지목된 항목만 수정 → 커밋
   └─ Review  reviewer: 이전 발견 사항만 재확인
   └─ 반복은 maxRounds까지. 그래도 FIX면 오케스트레이터가 사용자에게 보고
[오케스트레이터] 결과 확인 → 푸시 → 다음 작업 또는 분할
```

종료 상태:

- `pass`: 다음 작업으로 진행한다.
- `needs-attention`: maxRounds 후에도 must/should가 남음. 오케스트레이터가 남은 항목을 읽고 (a) 직접 한 번 더 fix 라운드를 돌리거나, (b) 작업을 나누거나, (c) 사용자에게 판단을 묻는다.
- `blocked`: builder가 카드 범위로는 불가능하다고 보고. 카드를 다시 쓴다.
- `agent-lost`: 에이전트가 응답 없이 종료. 같은 args로 재실행하면 완료된 단계는 캐시에서 복원된다.

## 3. 토큰 절약 규칙

작업 크기와 읽기 범위를 제한하는 것이 핵심이다. 아래 규칙은 카드와 에이전트 정의에 이미 반영돼 있다.

1. **한 번에 한 작업.** 워크플로 하나는 카드 하나만 다룬다. 여러 카드를 한 실행에 묶지 않는다.
2. **카드는 작게.** 새 코드 400줄 이하, 파일 6개 이하를 기준으로 한다. 넘으면 카드를 나눈다(예: T08·T09·T10처럼 화면을 셋으로 분할).
3. **읽기 범위 명시.** 카드의 "읽을 것"에 적힌 파일과 문서 절만 읽는다. 기획서·PPT·이미지는 카드가 지정하지 않는 한 읽지 않는다. 시나리오 문서는 필요한 절만 `sed -n` 범위로 읽는다.
4. **카드 추출.** builder와 reviewer는 `docs/TASKS.md` 전체가 아니라 자기 카드 절만 `awk '/^## T04 /{p=1;print;next} /^## T[0-9][0-9] /{p=0} p' docs/TASKS.md`로 읽는다.
5. **보고는 요약만.** 파일 내용·diff·전체 로그를 보고에 넣지 않는다. 검사 출력은 `| tail -30`.
6. **검토는 diff 기준.** reviewer는 작업 커밋의 diff만 본다. 트리 전체를 읽지 않는다. fix 라운드에서는 지목 항목만 재확인한다.
7. **반복 상한.** `maxRounds` 기본 2. 세 번째 라운드가 필요하면 카드가 잘못 잘린 것이므로 나눈다.
8. **구조화 출력.** builder·reviewer는 JSON 스키마로 답한다. 자유 서술을 줄이고 오케스트레이터가 파싱 없이 판단한다.
9. **재실행은 캐시.** 같은 스크립트·같은 args로 `resumeFromRunId`를 주면 끝난 단계는 다시 돌지 않는다.
10. **오케스트레이터도 절약.** 결과 객체의 `openFindings`와 `summary`만 읽고 판단한다. 에이전트 transcript는 문제가 있을 때만 연다.

## 4. 실행 방법

오케스트레이터(이 세션)에 "T01 실행"이라고 말하면 아래를 수행한다.

```
Workflow({ name: "task-cycle", args: { task: "T01", maxRounds: 2 } })
```

이름으로 찾지 못하는 환경에서는 경로로 실행한다.

```
Workflow({ scriptPath: ".claude/workflows/task-cycle.js", args: { task: "T01", maxRounds: 2 } })
```

선택 인자: `buildModel`, `reviewModel`(예: `"opus"`), `attribution`(커밋 메시지 끝에 붙일 줄).

여러 작업을 이어서 할 때는 오케스트레이터가 한 작업이 `pass`로 끝난 뒤 푸시하고 다음 작업을 시작한다. 의존성이 없는 카드(예: T03과 T07)는 순서를 바꿔도 되지만 같은 파일을 건드리는 카드를 동시에 돌리지 않는다.

## 5. 오케스트레이터의 판단 규칙

- `pass`인데 `nits`가 있으면 다음 작업 카드의 "읽을 것"에 붙여 보내거나 무시한다. 별도 라운드를 돌리지 않는다.
- `needs-attention`에서 남은 항목이 must 하나뿐이고 위치가 명확하면 오케스트레이터가 직접 고치고 커밋한다. 둘 이상이면 카드를 나눈다.
- reviewer가 카드 자체의 결함(모순된 완료 조건)을 지적하면 카드를 고친 뒤 재실행한다. builder에게 카드를 해석하게 두지 않는다.
- 마일스톤(DEV_PLAN 5절)이 끝나면 오케스트레이터가 지시서 7장 완료 기준 중 해당 항목을 체크리스트로 갱신해 docs/TASKS.md 상단에 기록한다.
- 사용자 보고는 마일스톤 단위로 한다. 작업마다 보고하지 않는다.

## 6. 왜 이 구조인가

- builder와 reviewer를 분리해 같은 모델이 자기 코드를 관대하게 보는 문제를 줄인다.
- 카드에 완료 확인 명령을 적어 두어 "됐다"는 말이 아니라 검사 결과로 판정한다.
- 시나리오 문서의 대표 경로표를 테스트 데이터로 옮기게 해(T04) 문서와 코드가 어긋나면 reviewer가 아니라 CI가 잡는다.
- 워크플로가 결정적이라 어디까지 됐는지 항상 알 수 있고, 중단 후 재개가 된다.

## 7. Codex 교차 검토

builder·reviewer는 같은 계열 모델이라 같은 맹점을 공유할 수 있다. 다른 모델(OpenAI Codex)의 검토를 PR 단위로 끼워 넣는다. Codex는 이 환경에 설치돼 있지 않으므로 GitHub 연동(PR 코멘트 트리거)으로만 부른다. 사전 조건: 사용자가 Codex 설정에서 이 저장소를 GitHub에 연결해 두어야 한다.

| 시점 | 오케스트레이터가 하는 일 |
| --- | --- |
| 마일스톤(DEV_PLAN 5절)이 끝나 푸시한 직후 | PR에 `@codex review` 코멘트를 남기고 PR 활동을 구독한다 |
| 머지 전 | 마지막으로 한 번 더 `@codex review` |
| 실측 결과·프롬프트 변경(T34·T35) 뒤 | `server/prompts/` 변경분만 짚어 검토를 요청한다 |

Codex 검토 결과 처리 규칙:

1. 지적은 reviewer의 finding과 같은 등급(must/should/nit)으로 읽는다. must·should는 고치고 푸시한 뒤 해당 스레드에 답글로 무엇을 고쳤는지 적고 resolve한다.
2. 스펙과 어긋나는 지적(예: 표결 규칙을 바꾸라는 제안)은 고치지 않고, 근거 문서 절을 들어 스레드에 답한다. 판단이 갈리면 사용자에게 묻는다.
3. Codex가 고친 코드를 직접 푸시하지 않게 한다(`@codex fix`는 쓰지 않는다). 수정은 이 세션의 builder 또는 오케스트레이터가 한다. 커밋 규칙(트레일러·모델명 금지)을 지키기 위해서다.
4. 처리 결과는 docs/TASKS.md "진행 상황" 표의 해당 행 비고에 "Codex 검토 n건 반영"으로 남긴다.
5. 10분 안에 Codex 응답이 없으면 연동이 안 된 것이다. 사용자에게 알리고 기다리지 않는다.
